# План дня: документ, правила и отказы

План приезжает одним JSON-документом на `POST /api/v1/day/{date}/plan` и заменяет прежний целиком. Отдаётся обратно внутри `GET /api/v1/day/{date}` — секциями, пунктами, расписанием и списком наложившихся окон.

Этот файл — то, что читает `/day-open` перед тем, как собрать план. Устройство суток — в `day-boundary.md`; канон дня (потолок часов, планка задач, якоря) — строка `day_rule_set`, см. ADR-0014 Р2.

## Почему документ, а не пункты по одному

Два ограничения канона — свойства плана, а не строки:

- **планка рабочих задач** (`day_rule_set.max_work_tasks`) считает задачи всего дня;
- **жёсткость** разрешена только краям дня, а какие края обязательны, говорит `required_anchors` того же правила.

Проверить их построчно нельзя. Триггер в базе тоже не годится: он сорвал бы импорт исторических дней ([#89]), которые планку нарушали, — а это ровно те дни, ради которых импорт и делается.

Поэтому план целиком приходит, целиком проверяется и целиком отвергается. Отказ не удаляет прежний план: документ судится до того, как удалена первая строка.

## Форма документа

```json
{
  "title": "План 2026-08-31 (пн)",
  "lede": "Понедельник: четыре задачи, стоп в 16:00",
  "purpose_md": "M1 «переезд» — закрыть висящий ответ",
  "status": "active",
  "source": "day-open",
  "sections": [
    {
      "title": "Якоря",
      "kind": "anchors",
      "items": [
        { "kind": "anchor", "rigidity": "hard", "code": "подъём", "text_md": "Подъём 06:00" }
      ]
    },
    {
      "title": "Работа",
      "kind": "work",
      "items": [
        {
          "kind": "task",
          "code": "W1",
          "text_md": "Ответить Sylvia",
          "window": "09:00-09:15",
          "done_criterion": "письмо отправлено, любое из двух",
          "quarter_goal_id": 1,
          "external_ref": { "clickup": "86cbau6mb" },
          "extra": { "Формат": "аудио" },
          "children": [
            { "kind": "minimum", "code": "W1-min", "text_md": "Хотя бы черновик" }
          ]
        }
      ]
    }
  ]
}
```

**Порядок — это позиция в списке.** Ни у секции, ни у пункта нет поля `ord`: номера ставит сервер. Клиентский номер на одну правку отстоит от двух секций, претендующих на одно место, и база такой план отвергнет, хотя в редакторе он выглядел целым.

**Окно — «ЧЧ:ММ-ЧЧ:ММ» по местным часам.** Не пара timestamp: и человек, и `/day-open` думают настенными часами, а знание про пояс и границу суток живёт в одном месте ([#107]). Конец раньше начала — окно через полночь: `23:30-00:30` даёт 60 минут, потому что день идёт от 04:00 до 04:00 и обе точки принадлежат одному дню. Хвост окна, который не время («пока ногти»), — в `window_comment`.

**Минимум — дочерний пункт, а не поле.** 29 августа показало: минимум, объявленный внутри задачи и без своей галки, не выполняется. Он приезжает как вложенный пункт `kind: "minimum"` и получает собственную отметку в [#88].

## Словарь полей пункта

Шесть подписей из живых планов закрыты в колонки — по ним нужны запросы и проверки:

| Подпись в файле | Куда едет |
| --- | --- |
| `Окно ::` | `window` → `starts_at`/`ends_at`, хвост в `window_comment` |
| `Сделано ::` | `done_criterion` |
| `Минимум ::` | отдельный дочерний пункт `kind: "minimum"` |
| `ClickUp ::` | `external_ref` |
| `Почему ::` | `why_md` |
| `Ход ::` | `plan_md` |

Всё остальное — `Факт`, `Формат`, `Вход`, `Материал`, `Репозиторий`, `Что писать` — едет в `extra` как есть, без схемы и без потери. В живых планах 28-31 августа таких подписей больше пятнадцати; заводить колонку под каждую значило бы менять схему на каждую новую формулировку.

## Что отвергается и как это звучит

Отказ — 422 с телом, которое **называет пункт**, а не «validation error»:

```json
{
  "error": "too_many_tasks",
  "message": "в плане 5 рабочих задач, канон разрешает 4…",
  "item_code": "W5",
  "item_text": "задача W5"
}
```

| `error` | Правило |
| --- | --- |
| `too_many_tasks` | Задач больше `max_work_tasks`. Назван код первой лишней |
| `free_item_has_window` | У пункта свободного блока проставлено окно — «не перезакручивать» |
| `task_without_window_or_criterion` | У задачи нет окна или критерия «сделано» (канон от 2026-08-28) |
| `task_is_not_linked` | У задачи нет ни `quarter_goal_id`, ни `unlinked_reason` |
| `hard_is_not_an_edge` | Жёстким объявил себя не край дня |
| `hard_anchor_is_not_in_canon` | Жёсткий якорь не назван в `required_anchors` правила |
| `bad_window` | Окно не читается как `ЧЧ:ММ-ЧЧ:ММ` |

## Где правило живёт на самом деле

Четыре правила — CHECK-ограничения таблицы `plan_item`, а не проверки сервиса. Значит, они верны и для импорта, и для миграции, и для сессии `psql`:

- `kind <> 'task' OR (starts_at IS NOT NULL AND ends_at IS NOT NULL AND done_criterion IS NOT NULL)`
- `rigidity <> 'free' OR starts_at IS NULL`
- `kind <> 'task' OR quarter_goal_id IS NOT NULL OR unlinked_reason IS NOT NULL`
- `starts_at IS NULL OR ends_at > starts_at`

Сервис (`app/day/plan_validate.py`) повторяет их — но только чтобы превратить «нарушено ограничение `ck_plan_item_free_has_no_window`» в «у пункта E1 свободного блока стоит окно». Расходятся — права база, а баг в сервисе; поэтому каждая ветка сервиса покрыта ещё и тестом, который пишет мимо него прямо в таблицу.

Одна оговорка на будущее: обратное окно до CHECK не доходит. Генерируемая колонка `window` считается раньше, и `tstzrange(23:30, 00:30)` падает сама — отказ приходит ошибкой диапазона, а не именем ограничения. Ограничение при этом на месте и верно, просто не успевает сработать.

## Наложения окон

`GET /api/v1/day/{date}` отдаёт `plan.overlaps` — пары пунктов, чьи окна пересекаются. Это самосоединение по `&&` поверх GiST-индекса на генерируемой колонке `window`, а не пересчёт на рендере: наложение — факт о сохранённом плане, и экран должен быть его потребителем, а не единственным владельцем.

`tstzrange` полуоткрыт, поэтому 09:00-10:00 и 10:00-11:00 стоят встык и наложением не считаются.
