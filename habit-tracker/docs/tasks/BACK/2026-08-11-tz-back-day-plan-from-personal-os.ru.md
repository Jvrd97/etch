# ТЗ · План дня из personal-os внутри Habit Tracker

## Цель

Сейчас план дня живёт в markdown-файле в другом репозитории, и чтобы его посмотреть, нужно
открыть редактор. Хочется видеть план там же, где уже отмечаются привычки — на экране Today, —
и отмечать выполненное оттуда.

Что должно получиться: personal-os отдаёт свой план дня в Habit Tracker, приложение показывает
его и позволяет ставить галочки; вечером personal-os забирает галочки обратно и кладёт факт
в свой итог дня. Markdown остаётся источником истины по содержанию плана, приложение —
источником истины по отметкам «сделано».

**Как сейчас.** В бэкенде есть категории с полями (EAV), записи по датам (`entries` +
`entry_values`), журнал, инсайты, онбординг, `daily-summary` и health. Все роутеры под
`API_V1_PREFIX = /api/v1` и зависимостью `require_api_key` (заголовок `X-API-Key`, пустой ключ
= dev-режим). У категорий есть флаг `show_in_today` (tri-state), то есть экран Today уже
существует и уже умеет решать, что на нём показывать. Плана дня в модели нет вообще: ни таблицы,
ни эндпоинта, ни понятия «задача на дату, пришедшая извне». Записи (`entries`) для этого не
годятся — они привязаны к `category_id` и описывают измерение привычки, а не список дел.

**Направление потока.** В PRD personal-os зафиксировано обратное направление: habit_tracker
отдаёт якоря и HealthKit в personal-os. Эта задача добавляет второе направление, а не заменяет
первое. Итог: план идёт `personal-os → tracker`, отметки идут `tracker → personal-os`, health
идёт `tracker → personal-os`. Каждое поле имеет ровно одного писателя — пересечений нет.

## Схема данных

Две таблицы. Отдельные от `entries` намеренно: у плана другой жизненный цикл (перезаписывается
целиком при каждой синхронизации) и нет привязки к категории.

**`day_plans`**

| Поле | Тип | Описание |
|---|---|---|
| `id` | int PK | |
| `plan_date` | date, unique, index | дата плана; один план на дату |
| `source_path` | varchar(500) | путь исходного md, для отладки |
| `content_hash` | varchar(64) | sha256 разобранного содержимого; по нему отсекается повторная запись того же плана |
| `header_note` | text, null | шапка плана (строка «ради чего сегодня», заметки о сдвиге дня) |
| `synced_at` | timestamptz | когда пришёл последний раз |
| `created_at` / `updated_at` | timestamptz | |

**`day_plan_items`**

| Поле | Тип | Описание |
|---|---|---|
| `id` | int PK | |
| `day_plan_id` | int FK → `day_plans.id`, ON DELETE CASCADE, index | |
| `block` | varchar(50) | секция плана: `anchors`, `training`, `work`, `study`, `growth`, `personal`, `extra` |
| `priority` | varchar(10), null | `P1` / `P2`, если в исходнике проставлен |
| `text` | text | текст пункта без markdown-разметки |
| `external_id` | varchar(50), null | id задачи ClickUp, если в строке была ссылка |
| `external_url` | varchar(500), null | ссылка на задачу |
| `order` | int | порядок внутри блока, как в файле |
| `stable_key` | varchar(64), index | sha256 от `block + external_id \|\| text`; переживает переформулировку **только** при наличии `external_id` |
| `done` | bool, default false | **пишет только приложение** |
| `done_at` | timestamptz, null | |

**Ключевой инвариант: `done` и `done_at` никогда не перезаписываются синхронизацией.**
При повторной синхронизации отметки переносятся на новые строки по `stable_key`. Пункт,
которого нет в новом плане, удаляется вместе с отметкой; пункт с изменённым текстом и без
`external_id` считается новым и приходит неотмеченным.

Миграция обратима: `downgrade` дропает обе таблицы. Данных, которых нет в markdown, кроме
отметок `done`, в них не хранится — потеря таблиц не теряет план.

## Эндпоинты

Все под `/api/v1`, все под `require_api_key`. Роутер `app/api/day_plan.py`, префикс `/day-plan`,
тег `day-plan`.

**`PUT /api/v1/day-plan/{plan_date}`** — принять план на дату (upsert).

- Вход: `DayPlanUpsertRequest` — `source_path`, `header_note`, `items[]` (`block`, `priority`, `text`, `external_id`, `external_url`, `order`).
- Выход: `DayPlanResponse` — план целиком с `id` пунктов и текущими `done`.
- Поведение: одна транзакция. Считается `content_hash`; если совпал с сохранённым — ничего не пишем, возвращаем существующий план и `status: "unchanged"`. Иначе строки пересобираются, а `done`/`done_at` переносятся по `stable_key`.
- Ошибки: `422` — пустой `items` или неизвестный `block`; `400` — `plan_date` в запросе не совпадает с датой в пути.

**`GET /api/v1/day-plan/{plan_date}`** — план на дату. `404`, если плана нет.

**`GET /api/v1/day-plan/today`** — то же для сегодняшней даты. Отдельный путь нужен, чтобы клиент не считал дату сам. `404`, если плана на сегодня нет — не пустой объект: «плана нет» и «план пустой» это разные состояния.

**`PATCH /api/v1/day-plan/{plan_date}/items/{item_id}`** — отметить пункт.

- Вход: `{"done": true}`.
- Выход: обновлённый пункт.
- `done_at` ставится сервером в момент перехода `false → true` и обнуляется при обратном. Клиент время не присылает.
- Ошибки: `404` — пункта нет или он принадлежит другой дате.

**`GET /api/v1/day-plan/{plan_date}/progress`** — сводка для обратной синхронизации: по каждому блоку `total`, `done`, и список `stable_key` отмеченных. Нужна, чтобы personal-os вечером забрал факт одним запросом, а не тянул план целиком и не диффил его сам.

## Разбор markdown

Парсер `app/services/day_plan_parser.py`, чистая функция: текст → структура. Без обращения к БД,
покрывается unit-тестами на реальных файлах планов.

Что распознаётся:

- Заголовки второго уровня — блоки. Соответствие русских заголовков ключам `block` задаётся словарём в коде: «Якоря» → `anchors`, «Тренировка» → `training`, «Работа» → `work`, «Учёба» → `study`, «Развивающий блок» → `growth`, «Личное/быт» → `personal`, «Extra» → `extra`. Неизвестный заголовок → блок `extra`, а не ошибка: план пишет человек, и он придумает новую секцию.
- Заголовки третьего уровня вида «P1 — …» / «P2 — …» задают `priority` для пунктов ниже, до следующего заголовка.
- Пункты — строки `- [ ]` и `- [x]`. Состояние галочки в исходнике **игнорируется**: `done` принадлежит приложению.
- Markdown-ссылка `[id](url)` в начале пункта → `external_id` и `external_url`, текст пункта берётся после тире.
- Строки без чекбокса внутри блока — не пункты. Абзацы до первого заголовка — `header_note`.

Парсер живёт на стороне бэкенда, а не в скрипте синхронизации: правила разбора — часть контракта
и должны быть покрыты тестами вместе с ним.

## Приёмка

- Миграция применяется и откатывается на чистой базе.
- `PUT` дважды подряд с тем же содержимым: второй раз возвращает `status: "unchanged"`, `updated_at` не меняется, `id` пунктов сохраняются.
- Отметил пункт → повторный `PUT` того же плана → отметка на месте.
- Отметил пункт → в новом плане этот пункт переформулирован, но `external_id` тот же → отметка на месте.
- Отметил пункт → в новом плане пункта нет → пункт исчез, ошибки нет.
- `GET /today` без плана на сегодня возвращает `404`, а не пустой объект.
- `PATCH` на чужой `item_id` возвращает `404`, а не молча меняет.
- Парсер разбирает реальные файлы `plans/2026/08/2026-08-10.md` и `2026-08-11.md` без потери пунктов; на файлы есть фикстуры в тестах.
- Все эндпоинты требуют `X-API-Key` — запрос без него даёт `401`.
- `mypy --strict` и `ruff` чисто, `pytest` зелёный.

## Что НЕ делаем

- **Экран.** Как план выглядит на Today, что сворачивается, как показывается прогресс — не эта задача. Здесь только контракт.
- **Расписание и напоминания.** Времени блоков в модели нет; план — список пунктов, а не календарь.
- **Мультипользовательность.** Приложение однопользовательское, `user_id` не вводим (как и в существующих таблицах).
- **Редактирование плана из приложения.** Менять можно только `done`. Текст пунктов правится в markdown — иначе появляется второй писатель и расхождение.
- **Автозапуск синхронизации.** Скрипт на стороне personal-os и вызов из `/day-open` и `/day-close` — отдельная задача в том репозитории.
- **История планов и аналитика.** Таблицы хранят все даты, но эндпоинтов «за период» и статистики в этой задаче нет.
- **Челлендж дня от LLM.** Обсуждался отдельно, к плану отношения не имеет.

## Не твоя зона, но блокирует приёмку

- **Решение, где хранится `done` по якорям.** Якоря (спорт, медитация, отбой) сейчас отмечаются в markdown, а после этой задачи их можно будет отметить и в приложении. Пока не решено, кто из двух прав при расхождении. Предложение по умолчанию: приложение, потому что отметка ставится в момент действия, а markdown заполняется вечером по памяти. Нужно подтверждение Daniil до приёмки.
- **Как personal-os получает сеть до контейнера.** Если бэкенд не поднят в момент `/day-close`, синхронизация должна деградировать молча, а не ронять закрытие дня. Поведение скрипта — задача personal-os, но требование сформулировать надо здесь.

## Открытые вопросы

1. Отметка задачи в приложении должна отражаться в ClickUp, если у пункта есть `external_id`? Сейчас в ТЗ — нет, ClickUp остаётся отдельным потоком. Если да — это третий писатель и отдельная задача с разбором конфликтов.
2. Нужен ли `DELETE /day-plan/{date}`? Пока не заложен: план перезаписывается через `PUT`, а удалять его незачем.
