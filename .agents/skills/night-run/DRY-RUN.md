# Сухой прогон ночного цикла — 2026-08-30

Проверка перенесённой петли **без единого запуска сессии**. Запускалась ровно одна команда,
`issue-night.sh collect -n 12`; она только читает тикеты и пишет свой список в `.night/`.
`habit-tracker/` и `issues/` не тронуты: в `habit-tracker/` в этот момент шла волна B.

## Вердикт

**Запускать можно, но не сегодня и не раньше двух правок.**

Механика цела: синтаксис чистый, пути на месте, параллельность физически отключена,
красные проверки не коммитятся. Ломает картину не код, а данные и одна дыра в надёжности.

| | |
|---|---|
| Сегодня прогон **не стартует** | preflight упрётся в грязное дерево волны B (15 файлов). Это правильное поведение, а не поломка |
| До запуска **обязательно** | перенести `90` и `93` в `done/` — иначе 23 тикета заморожены навсегда |
| До запуска **желательно** | обернуть `claude -p` во внешний таймаут: часовой лимит на сессию отсутствует вообще |
| Выхлоп ночи | потолок 20 тикетов за 4 волны, если всё зелёное. С разморозкой `90`/`93` — заметно больше |

### Поломка: `already-committed` не доходит до графа зависимостей

## 6. Красные проверки не коммитятся

`issue-watcher.sh:385-401`, первое, что делает `finish_pass`:

```bash
finish_pass() {
  local issue="$1" result="$2" subject hash
  if ! gate_checks; then
    log "[$ID] проверки красные — НЕ коммичу"
    park_worktree "$ID" "red-checks"
    python3 - "$result" <<'PY'
...
d["status"] = "BLOCKED"
d.setdefault("blockers", []).insert(0, "проверки перед коммитом красные, работа убрана в git stash")
...
PY
    printf ... "BLOCKED_CHECKS" ... >> "$SUMMARY"
    return 0
  fi
```

Возврат стоит **до** `commit_ticket` (404) и **до** `move_ticket "$issue" done` (412).
Красный тикет не коммитится, не уезжает в `done/` и остаётся в `in-work/` — утром видно,
за что брались и не доехали.

Что именно считается красным (`gate_checks`, 155-176): `ruff check`, `ruff format --check`,
`mypy --strict`, ровно одна alembic-голова, `pytest` обходной командой на 5432 — если
тронут бэкенд; `bun test`, `tsc --noEmit`, `bun run lint` — если тронут фронтенд.

**Дыра здесь одна.** Оба блока условны (`touched "$BACKEND_DIR"` / `touched "$FRONTEND_DIR"`).
Тикет, чей дифф лёг мимо обеих папок — например только в `habit-tracker/ios/` — проходит
`gate_checks` зелёным, не выполнив **ни одной** проверки, и коммитится: `git add`
захватывает весь `habit-tracker`. Native-тикеты отсеиваются на сборе, так что вероятность
низкая, но гарантии нет. Дешёвая заплатка: если ни один из блоков не отработал, а дифф
непустой — считать проверки красными.

## 7. Риски ночи

### Упадёт API

Обработано. `rc != 0` → пауза `30 × attempt` (30/60/90 с) → лестница `resume → resume →
fresh`, до `RETRIES=4` попыток, дальше `EXHAUSTED` и stash. Отдельная ветка на `rc = 0`
без файла результата: переход в `mode=direct`, петля без инструмента Workflow.

**Слабое место — 429.** Детектор один: `json_field "$out" api_error_status` = `"429"`
(строка 328). `json_field` глушит ошибки через `2>/dev/null`, поэтому если `claude`
умрёт от лимита, не дописав JSON, поле не найдётся, флаг `.night/ratelimit.stop`
не встанет и каждый оставшийся тикет сожжёт свои 4 попытки с паузами. Не катастрофа
(≈3 минуты сна на тикет), но заявленный «останов всего прогона на первом 429» в этом
сценарии не сработает. Проверяемо только живым прогоном.

**Ещё: исчерпанный тикет получает второй полный круг.** Подпись волны считается на
строке 239 — **до** `move_to_inwork` (245). После первой волны список тех же тикетов уже
содержит пути `in-work/`, подпись другая, волна повторяется. Останов наступит только на
третьей. Итого 8 попыток вместо 4. Лечится переносом `sig=` под `move_to_inwork`.

### Кончится место на диске

Свободно 18 GiB, репозиторий 1.1 GiB. Логи ночи — килобайты, риск не в них, а в
`bunx tsc` (тянет typescript) и сборках колёс `uv`.

Обработано частично: `git stash push` при полном диске упадёт, ветка `else` в
`park_worktree` (199-202) поставит `.night/dirty.stop` и **следующий тикет не стартует**.
Это правильная реакция. Но: `run_issue` возвращает `1`, а цикл на 430 возврат
игнорирует, и `SKIPPED_DIRTY_TREE` не попадает в проверку `grep EXHAUSTED` на 437 —
прогон закончится кодом 0, хотя половина тикетов пропущена. Утром это видно только
в `.night/summary.tsv`.

Записи в `.night/` при полном диске упадут молча (`2>/dev/null`, `>>`).

### Повиснет `claude -p`

**Не обработано вовсе. Это главный риск ночи.**

Ни `timeout`, ни `gtimeout`, ни фонового сторожа — ни в одном скрипте. Единственный
предел на сессию — `--max-budget-usd 12`, а это лимит **денег**, а не времени: сессия,
залипшая на сетевом чтении или на промпте разрешения (в режиме `--ask-perms`), не тратит
токенов и висит вечно. Лок при этом занят, следующий тикет не начнётся, к утру сделан
ноль тикетов, и определить это можно только по `.night/live/<id>.json`.

`BASH_DEFAULT_TIMEOUT_MS=600000` (строка 99) ограничивает **отдельную Bash-команду
внутри** сессии, а не саму сессию.

Заплатка на одну строку, в обеих ветках вызова (315 и 319):

```bash
timeout "${NIGHT_SESSION_TIMEOUT:-5400}" claude -p --name "night-$ID" …
```

На macOS `timeout` нет в базе — либо `gtimeout` из coreutils, либо сторож на
`&` + `sleep` + `kill`. Без этого автономная ночь остаётся ставкой на то, что CLI
никогда не залипнет.

### Ещё две мелочи

`gate_checks` считает головы как `alembic heads | grep -c '[^[:space:]]'`. Любое
предупреждение alembic на stdout даст счётчик > 1 и ложную красноту.

Команды фронтенда (`bun --cwd=… test`, `bunx tsc -p …`, `bun run lint`) в этом прогоне
**не проверялись**: их запуск задел бы `habit-tracker/`, где шла волна B. Прогнать вручную
до первой ночи.
