# Habit Tracker — общий контекст (преамбула ко всем запросам на редизайн)

Этот файл прикладывается **первым** к любому запросу на редизайн конкретного экрана.
Второй файл — брифинг нужного экрана (`01-dashboard.md` … `09-onboarding.md`).

Всё собрано из реального кода и документации репозитория на 2026-07-30.

---

## 1. Продукт

Персональный трекер привычек и состояния организма для **одного пользователя** (владелец = разработчик).
Задуман не как «милый wellness-апп», а как «операционная система организма»: строгий технологичный
интерфейс, ощущение дорогого прибора. Референсы вдохновения: Whoop, Linear, Arc, Nothing, Raycast, DevTools.

Два отличия от массовых трекеров:

**Полностью пользовательская модель данных.** Пользователь сам создаёт категории («Отжимания», «Кофе»,
«Сон», «Курение») и сам определяет для каждой набор полей произвольного типа. Приложение не навязывает
ни списка привычек, ни единиц, ни «правильного» способа считать успех.

**AI-разбор периода.** Агрегаты за период плюс тексты дневника уходят в LLM, который возвращает
markdown-отчёт: тренды, пропуски, корреляции и 2–3 рекомендации, на русском.

Главный сценарий — телефон, в моменте: «записал 42 отжимания за ≤3 тапа». Это зафиксированный
критерий приёмки из PRD.

## 2. Стек и ограничения платформы

| Слой | Технологии |
|---|---|
| Backend | FastAPI, SQLAlchemy 2.0 async, Alembic, PostgreSQL 16 |
| Frontend | Next.js App Router, TypeScript strict, TailwindCSS, lucide-react, Recharts, Bun |
| Мобильный веб | отдельный shell `/m` в том же проекте: свои страницы, нижний tab bar |
| iOS | SwiftUI, iOS 17+ — спроектирован, **ещё не написан** |
| LLM | Anthropic claude-sonnet-5 через SDK **или** `claude -p` CLI; слой `app/llm/` |
| Инфра | Docker Compose, VPS, доступ только внутри Tailscale + заголовок `X-API-Key` |

Аутентификации и пользователей нет принципиально: single-user, периметр = сеть плюс статический ключ.
Из этого следует важное для дизайна: **нет профиля, нет имени пользователя, нет аватара, нет настроек аккаунта.**

Правила кода, которые влияют на дизайн-решения:

- TypeScript strict, `any` запрещён.
- Логика экрана живёт в хуке (`hooks/useX.ts`), чистые вычисления — в `lib/*.ts` с юнит-тестами.
  Десктоп и `/m` делят логику и различаются только разметкой. Любой новый расчёт — это чистая функция плюс тест.
- Иконки — только `lucide-react`. Графики — Recharts.
- Минимальная зона тапа 44 px.

## 3. Модель данных

### Category

```
id, name (уникально), description?, icon?, color? (HEX),
display_mode: 'form' | 'checklist',
streak_mode:  'build' | 'avoid',
group: string | null,
show_in_today: boolean | null,   // добавляется прямо сейчас, ещё не в main
is_active: bool,
created_at, updated_at,
fields: Field[]
```

- `display_mode='checklist'` — категория рисуется набором чекбоксов (несколько boolean-полей).
- `display_mode='form'` — категория рисуется формой с полями.
- `streak_mode='avoid'` — «не срываться» (курение, сахар): считается серия чистых дней.
- `streak_mode='build'` — «набирать» (спорт, чтение): **серии для них не считаются** (см. §5).
- `group` — свободная строка, по ней строятся вкладки в таблице; пусто → `Other`.
- `show_in_today` — явное решение пользователя, показывать ли категорию на экране Today;
  `null` означает «решай эвристикой».

### Field

```
id, category_id, name, order,
field_type: 'text' | 'number' | 'boolean' | 'date' | 'datetime' | 'time' | 'select' | 'duration',
is_required, options?   // строка через запятую, для select
```

**Единицы измерения у поля нет.** «42» — это отжимания или минуты, знает только имя поля.

### Entry (запись)

```
id, category_id,
entry_date: DATE,        // календарный день, без времени суток
notes?,
idempotency_key?,        // дедупликация оффлайн-очереди
created_at, updated_at,  // timestamptz — момент фактического сохранения
values: EntryValue[]     // { field_id, value } — value ВСЕГДА строка (EAV)
```

Критично: у записи **нет пользовательского времени события**, только дата.
`created_at` — это когда запись физически создана; из него можно честно показать «14 минут назад»
и «сегодня, 09:15», но нельзя утверждать «тренировка была в 09:15».

За один день у категории может быть много записей (три подхода отжиманий — три записи).

### JournalEntry

```
id, title, content (markdown), entry_date, mood?, tags? (строка через запятую), created_at, updated_at
```

### AIReport

```
id, period_days, content (markdown, русский), model, created_at
```

## 4. Полный API

Базовый префикс `/api/v1`.

**Categories**
- `GET /categories?active_only=true` — список категорий с полями
- `GET /categories/{id}` · `POST /categories` · `PATCH /categories/{id}` · `DELETE /categories/{id}`
- `POST /categories/{id}/fields` — добавить поле
- `POST /categories/batch` — транзакционно применить план операций (онбординг)
- `GET /categories/{id}/streak` → `{ category_id, streak_mode, current_streak, best_streak, last_relapse_date }`
  — **по одной категории за запрос**, массового эндпоинта нет

**Entries**
- `GET /entries?category_id&start_date&end_date&skip&limit`
- `GET /entries/{id}` · `POST` · `PATCH` · `DELETE`
- `PUT /entries/checklist` — upsert чек-листа за день: `{category_id, entry_date, values: {field_id: bool}}`
- `GET /entries/category/{id}/range?start_date&end_date`

**Table** — единственный агрегирующий эндпоинт
- `GET /table?date_from&date_to` (диапазон до 366 дней) →

```
{
  categories: [{ id, name, display_mode, group,
                 primary_field_id, primary_field_name, primary_field_type }],
  days: [{ date, cells: [{ category_id, field_id, aggregated_value, entry_count }] }]
}
```

Агрегацию за день считает бэкенд, едино для всех клиентов:
`number → sum`, `boolean → any`, `text/select/date → последнее значение`.
`entry_count` — сколько записей сложилось в ячейку.

**Journal**
- `GET /journal?start_date&end_date&mood&search&skip&limit` → `{ total, items[] }`
- `GET /journal/{id}` · `POST` · `PATCH` · `DELETE` · `GET /journal/date/{date}`

**Insights (AI)**
- `POST /insights { period_days: 1..366 }` → полный markdown-отчёт; генерация до пары минут
- `GET /insights` → список с превью (первые ~200 символов)
- `GET /insights/{id}`

Промпт требует ровно четыре секции на русском: **Тренды / Пропуски / Корреляции / Рекомендации**
(последняя — ровно 2–3 конкретных действия), весь отчёт до ~400 слов. В контекст модели уходят дневные
агрегаты из `/table` плюс записи дневника (title, mood, tags, полный текст), максимум 200 записей.

**Onboarding**
- `POST /onboarding/draft { transcript }` → план операций (`create_category` / `add_field`), только превью;
  применяется через `POST /categories/batch`.

## 5. Чего в системе нет (жёсткие рамки)

Если дизайн требует что-то из этого списка — это backend-тикет, и его надо назвать явно.

- **Нет целей и норм.** У категории и поля нет `target`/`goal`. «Выполнено 3 из 5», «68 % нормы»,
  кольцо «до цели» — наполнять нечем. Текущее кольцо на дашборде заполняется от константы, это заглушка.
- **Нет единиц измерения** (`reps`, `ml`, `min`, `h`). Есть только имя поля.
- **Нет времени события** у записи, только дата плюс `created_at`.
- **Нет серий для build-категорий.** Эндпоинт стриков считает всё в avoid-семантике: срыв — день,
  где boolean равен true или number больше нуля; день без записей считается чистым. Для `build`
  числа бессмысленны, и UI обязан их прятать. «Стрик тренировок» пока нельзя.
- **Нет массового эндпоинта стриков** — N категорий это N запросов.
- **Нет серверных агрегатов за неделю/месяц** и сравнения периодов. Только дневные ячейки;
  «за 7 дней» и «+18 % к прошлому периоду» надо складывать на клиенте из `/table`.
- **Нет расписания привычек** (какая привычка в какие дни ожидается). Поэтому «пропущено 2 дня из 7» —
  это только «нет записей», а не «нарушен план».
- **Нет тегов как сущности** — `tags` дневника это строка.
- **Нет пользователей, профиля, настроек, уведомлений, поиска по приложению.**
- **Нет структурированного AI-вывода** — отчёт приходит одним markdown-полотном; «ключевые выводы
  тремя буллетами» надо либо парсить из markdown, либо менять контракт LLM-слоя.
- **Нет Apple Health** (сон, пульс, шаги) — это следующая фаза, данных сейчас нет вообще.
- **Нет офлайна в вебе** — очередь спроектирована для будущего iOS.
- **Нет пагинации** списков на фронте: `GET /entries` тянет весь список.

## 6. Дизайн-система «Lime Tech»

Утверждена 2026-07-22, канон для всех клиентов. Референс утверждённого редизайна дашборда —
`docs/design/dashboard-design-desktop.png` и `docs/design/dashborad-design-mobile.png`.

`#65a30d`, `#0284c7`, `#b45309`, `#9333ea`.

### Стиль

- Dark UI, glass плюс matte, скругления 20–28 px, много воздуха, минимум градиентов,
  без декоративных иллюстраций, без emoji в интерфейсе.
- Типографика Inter (web) / SF Pro Display (iOS): H1 36 Bold, Section 22 Semibold,
  Card 18 Medium, Body 16 Regular, Caption 13 Medium. Числа — `tabular-nums`.
- Иконки Lucide, stroke 2 px.
- Лайм — только акцент: активный таб, primary-кнопка, прогресс-кольцо, свечение при выполнении.
  Лайм не заливает большие площади.
- Loading — тонкое неоновое кольцо или пульс, не спиннер. Empty state — иконка, фраза, одна кнопка.
  Error — текст плюс Retry.
- Анимации: подъём карточек 2–4 px при касании, дорисовка колец 400–600 мс, fade+slide на смене вкладок.

### Навигация

Десктоп — верхняя навигация: `Dashboard · Today · Table · Categories · Entries · Journal · Insights`.
Мобайл (`/m`) — нижний tab bar на пять слотов: `Today · Entries · Dashboard · Categories · More`;
Table, Journal, Insights и Onboarding живут внутри «More».

У каждого экрана есть мобильный двойник. Любое дизайн-решение обязано иметь внятную мобильную
раскладку в одну колонку.

## 7. Язык интерфейса

Сейчас смешанный: каркас английский (`Dashboard`, `Log entry`, `Nothing here yet`), а AI-панель,
Insights и Онбординг — русские. Утверждённый макет редизайна дашборда сделан **на русском**
для мобайла и на английском для десктопа. Это расхождение надо закрыть: предполагаем единый русский,
но решение фиксируется отдельно.
