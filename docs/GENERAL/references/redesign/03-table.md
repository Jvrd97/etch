# Экран 3 — Table

Статус: редизайн не начат.

---

## 1. Назначение

Плотный обзор регулярности: строка — день, колонка — привычка. Экран, на котором одним взглядом
видно, где дыры в истории. Задуман (в дизайн-системе) в духе GitHub Contributions: интенсивность
цвета ячейки от значения, тап по ячейке — детали дня.

## 2. Что на экране сейчас

Заголовок `Table.` и «Last 14 days by group — tap a cell to see the day».

Вкладки по `category.group` (категории без группы попадают во вкладку `Other`). Внутри вкладки —
обычная HTML-таблица с горизонтальной прокруткой.

Колонки строятся динамически:
- Категория с `display_mode='checklist'` разворачивается в **одну колонку на каждое boolean-поле**;
  в заголовке крупно имя поля, мелко — имя категории.
- Категория-форма даёт одну колонку по своему primary-полю; в заголовке имя категории, мелко — имя поля.

Ячейки:
- Чек-бокс-колонка: галочка лаймом или прочерк; тап переключает значение (оптимистично, через
  `PUT /entries/checklist`).
- Значение-колонка: агрегат за день лаймом или прочерк. Тап по заполненной — панель дня;
  тап по пустой — сразу форма создания записи за этот день.
- `duration` форматируется в часы и минуты.

Панель дня — модалка со списком записей категории за дату: каждое поле редактируется инлайн,
запись можно сохранить или удалить, внизу кнопка «Add entry».

Пустое состояние: «No columns yet — Create a category with at least one field».

Мобильный двойник `/m/table` — та же логика, липкая колонка даты.

## 3. Данные

- `GET /table?date_from&date_to` за последние 14 дней — единственный источник сетки.
  Агрегация за день считается на сервере: `number → sum`, `boolean → any`,
  `text/select/date → последнее значение`. Плюс `entry_count` — сколько записей сложилось в ячейку.
- `GET /categories` — чтобы узнать boolean-поля чек-листов.
- Панель дня: `GET /entries?category_id&start_date&end_date`.
- Эндпоинт таблицы принимает диапазон **до 366 дней**, то есть год истории тянется одним запросом.

## 4. Проблемы текущего экрана

- Это буквально HTML-таблица: ровная сетка без визуального веса, ничем не отличающаяся от админки.
- Интенсивность значения никак не закодирована — «1 отжимание» и «100 отжиманий» выглядят одинаково.
  Задумка из дизайн-системы (heatmap) не реализована.
- Дата в ячейке — сырая ISO-строка, нет ни дня недели, ни выделения выходных, ни разделителей недель.
- `entry_count` не используется: не видно, что за числом стоит три подхода.
- Жёсткие 14 дней без выбора периода, хотя API отдаёт до года.
- При многих категориях горизонтальная прокрутка становится основным способом навигации.
- Заголовок колонки в две строки (имя поля плюс имя категории) читается тяжело.
- Нет ни итогов по колонке, ни итогов по строке — «сколько всего за день» и «сколько за 14 дней» негде взять.

## 5. Ограничения

- Никаких серверных агрегатов кроме дневных: недели и месяцы надо складывать на клиенте.
- Нет целей, поэтому раскрасить «выполнено / не выполнено» по норме нельзя — только по факту наличия.
- Нет единиц измерения.
- Строка дня существует для всех дат диапазона, но «нет записи» и «записал ноль» неразличимы визуально.

## 6. Чего ждём от редизайна

- Кодирование значения цветом или плотностью (heatmap), чтобы сетка читалась как картина, а не как отчёт.
- Работа с масштабом: 22 категории и год истории на одном экране — что сворачивается, что закрепляется.
- Выбор периода (7 / 14 / 30 / 90 дней) и внятная работа с горизонтальной прокруткой.
- Итоги: по дню и по привычке за период.
- Мобильная версия: таблица на телефоне — самый тяжёлый случай, нужен отдельный ответ.
- Что делать с двумя разными типами колонок (галочка и число), чтобы они жили в одной сетке.
