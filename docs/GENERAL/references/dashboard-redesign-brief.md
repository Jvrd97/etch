**# Habit Tracker — полный контекст проекта для редизайна Dashboard

Документ самодостаточный: его можно целиком отдать внешней модели (ChatGPT) как единственный вход.
Всё ниже собрано из реального кода и документации репозитория на 2026-07-30, а не по памяти.

Цель обращения: **переработать экран Dashboard** так, чтобы он стал информативнее и понятнее.
Остальные экраны — контекст, их менять не просим (пока).

## 1. Что это за продукт

Персональный трекер привычек и состояния организма для **одного пользователя** (владелец = разработчик).
Не «милый wellness-апп», а по замыслу — «операционная система организма»: строгий технологичный
интерфейс, ощущение дорогого прибора (референсы вдохновения: Whoop, Linear, Arc, Nothing, Raycast, DevTools).

Ключевая идея, отличающая от массовых трекеров: **полностью пользовательская модель данных**.
Пользователь сам создаёт категории («Отжимания», «Кофе», «Сон», «Медитация», «Курение») и сам
определяет для каждой набор полей произвольного типа. Приложение не навязывает ни списка привычек,
ни единиц измерения, ни «правильного» способа считать успех.

Второе отличие — **AI-разбор периода**: агрегаты + тексты дневника уходят в LLM, который возвращает
markdown-отчёт с трендами, пропусками, корреляциями и 2–3 рекомендациями на русском.

Основной сценарий использования: телефон, в моменте, «записал 42 отжимания за ≤3 тапа».
Целевой критерий из PRD — запись числового значения по существующей привычке за **не более 3 тапов**
от открытия приложения.

### Стек

| Слой | Технологии |
|---|---|
| Backend | FastAPI, SQLAlchemy 2.0 (async), Alembic, PostgreSQL 16 |
| Frontend (актуальный клиент) | Next.js (App Router), TypeScript strict, TailwindCSS, lucide-react, Bun |
| Мобильный веб | отдельный shell `/m` — тот же Next-проект, свои страницы и tab bar |
| iOS | SwiftUI, iOS 17+, SwiftData — запланирован, **ещё не написан** |

| Инфра | Docker Compose, VPS, доступ только внутри Tailscale + статический заголовок `X-API-Key` |

Авторизации/пользователей нет принципиально: single-user, периметр = сеть + ключ.

### Статус фаз

| Фаза | Что | Статус |
|---|---|---|
| PHASE-00 | Full-stack MVP (FastAPI + Next.js) | done (унаследовано) |

## 2. Модель данных (то, из чего вообще можно рисовать дашборд)

### Category

```
id, name (уникально), description?, icon?, color? (HEX),
display_mode: 'form' | 'checklist',
streak_mode:  'build' | 'avoid',
group: string | null,        // произвольная группировка, напр. "Спорт", "Здоровье"
is_active: bool,
created_at, updated_at,
fields: Field[]
```

- `display_mode = 'checklist'` — категория рисуется как набор чекбоксов (несколько boolean-полей).
- `display_mode = 'form'` — категория рисуется как форма с полями.
- `streak_mode = 'avoid'` — «не срываться» (курение, сахар): считается серия чистых дней.
- `streak_mode = 'build'` — «набирать» (спорт, чтение): **серии для них сейчас не считаются** (см. §4).
- `group` — свободная строка; в таблице по ней строятся вкладки, «без группы» → `Other`.

### Field

```
id, category_id, name,
field_type: 'text' | 'number' | 'boolean' | 'date' | 'datetime' | 'time' | 'select' | 'duration',
is_required, options? (строка для select), order
```

### Entry (запись)

```
id, category_id,
entry_date: DATE,       // ТОЛЬКО дата, без времени суток
notes?,
idempotency_key?,       // для дедупликации оффлайн-очереди
values: EntryValue[]    // { field_id, value } — value ВСЕГДА строка (EAV)
```

Критично для дизайна: **у записи нет времени суток**, только календарный день.
За один день у категории может быть много записей (например, 3 подхода отжиманий).

### JournalEntry (дневник)

```
id, title, content (markdown-ish текст), entry_date, mood?, tags? (строка), created_at, updated_at
```

### AIReport (сохранённый AI-разбор)

```
id, period_days, content (markdown, русский), model, created_at
```

## 3. Полный API (что реально можно запросить)

Базовый префикс `/api/v1`.

### Categories
- `GET /categories?active_only=true` — список категорий с полями
- `GET /categories/{id}`
- `POST /categories`, `PATCH /categories/{id}`, `DELETE /categories/{id}`
- `POST /categories/{id}/fields` — добавить поле
- `POST /categories/batch` — транзакционно применить план операций (используется онбордингом)
- `GET /categories/{id}/streak` → `{ category_id, streak_mode, current_streak, best_streak, last_relapse_date }`

### Entries
- `GET /entries?category_id&start_date&end_date&skip&limit` — плоский список записей
- `GET /entries/{id}`, `POST /entries`, `PATCH /entries/{id}`, `DELETE /entries/{id}`
- `PUT /entries/checklist` — upsert чек-листа за день (`{category_id, entry_date, values: {field_id: bool}}`)
- `GET /entries/category/{id}/range?start_date&end_date`

### Table (единственный агрегирующий эндпоинт)
- `GET /table?date_from&date_to` (диапазон ограничен 366 днями) →

```
{
  categories: [{ id, name, display_mode, group,
                 primary_field_id, primary_field_name, primary_field_type }],
  days: [{ date, cells: [{ category_id, field_id, aggregated_value, entry_count }] }]
}
```

Правила агрегации за день считает **бэкенд** (единая логика для всех клиентов):
`number → sum`, `boolean → any (есть хоть одна true)`, `text/select/date → последнее значение`.
`entry_count` — сколько записей сложилось в ячейку.

### Journal
- `GET /journal?start_date&end_date&mood&search&skip&limit` → `{ total, items[] }`
- `GET /journal/{id}`, `POST`, `PATCH`, `DELETE`, `GET /journal/date/{date}`

### Insights (AI)
- `POST /insights { period_days: 1..366 }` → полный markdown-отчёт (генерация занимает до пары минут)
- `GET /insights` → список отчётов с превью (первые ~200 символов)
- `GET /insights/{id}`

Промпт требует от модели ровно 4 секции на русском: **Тренды / Пропуски / Корреляции / Рекомендации**
(последняя — ровно 2–3 конкретных действия), весь отчёт < ~400 слов.
В контекст модели уходят: дневные агрегаты из `/table` + записи дневника (title, mood, tags, полный текст),
максимум 200 записей дневника.

### Onboarding (голосовой конструктор категорий, web-only)
- `POST /onboarding/draft { transcript }` → план операций (`create_category` / `add_field`), только превью,
  ничего не сохраняет; применяется через `POST /categories/batch`.

## 4. Что система УМЕЕТ и чего НЕ умеет (жёсткие рамки редизайна)

### Умеет (данные доступны прямо сейчас)

- Считать за любой день по любому полю: сумму чисел, «было/не было» для boolean, последнее значение для текста.
- Отдавать диапазон до 366 дней одним запросом → любые графики/хитмапы/тренды за год строятся на фронте.
- Считать серию «чистых дней» для avoid-категорий: `current_streak`, `best_streak`, `last_relapse_date`.
- Хранить произвольную группировку категорий (`group`) — уже используется как вкладки в таблице.
- Отдавать общее число записей дневника и фильтровать дневник по датам/настроению/поиску.
- Генерировать и хранить историю AI-разборов за 7/30/90 дней.
- Различать типы категорий: чек-лист vs форма, набираемая привычка vs избегаемая.

### НЕ умеет (нет в модели данных — если дизайн это потребует, нужен backend-тикет)

- **Нет целей и норм.** У категории/поля нет `target`, `goal`, `unit`. Значит «выполнено 3 из 5»,
  «68 % нормы», кольца прогресса «до цели» **нечем наполнить честно**. Текущее кольцо на дашборде
  заполняется от жёсткой константы `RING_TARGET_ENTRIES = 10` записей — это заглушка, а не смысл.
- **Нет единиц измерения.** «42» — это отжимания или минуты, знает только имя поля.
- **Нет времени суток у записей** (только дата) → нельзя «активность по часам», «утро/вечер».
- **Нет серий для build-категорий.** Эндпоинт стриков считает всё в avoid-семантике; для
  `streak_mode='build'` числа бессмысленны, и UI обязан их прятать. «Стрик тренировок» — пока нельзя.
- **Нет серверных агрегатов за неделю/месяц** и сравнения периодов (Δ к прошлой неделе). Только дневные
  ячейки; любые «за 7 дней» надо складывать на клиенте из `/table`.
- **Нет тегов как сущности** — `tags` дневника это просто строка.
- **Нет уведомлений, напоминаний, расписаний привычек** (какая привычка в какие дни ожидается).
  Поэтому «пропущено 2 дня из 7» вычислимо только как «нет записей», а не как «нарушен план».
- **Нет мультиюзерности, шаринга, соцфункций.**
- **Нет Apple Health / шагов / сна / пульса** — это PHASE-02, пока данных нет вообще.
- **Нет офлайна в вебе** (офлайн-очередь спроектирована для будущего iOS).

## 5. Экраны приложения сегодня

Навигация (десктоп — верхняя, мобильный `/m` — нижний tab bar):
`Dashboard · Today · Table · Categories · Entries · Journal · Insights · (Onboarding)`.
У каждого экрана есть мобильный двойник в `/m`; логика вынесена в общие хуки, различается только разметка.

| Экран | Что делает |
|---|---|
| **Dashboard** (`/`) | Витрина: кольцо с числом записей, панель AI-разбора, 3 KPI-плитки, лента последней активности, 3 quick actions. Разбирается ниже. |
| **Today** | Экран дня: категории раскладываются на три группы — avoid-карточки со счётчиком чистых дней, чек-листы (тап = отметка), быстрые числовые поля (`+1`, ручной ввод). Оптимистичные апдейты с откатом при ошибке. |
| **Table** | Сетка «строка = день (последние 14), колонка = привычка», вкладки по `group`. Чек-лист-категории разворачиваются в колонку на каждое boolean-поле, form-категории показывают primary-поле. |
| **Categories** | CRUD категорий и полей. Детальная страница категории: график (line-серии по number/time-полям, бары для чек-листов, периоды 7d/30d/90d/all), блок стрика, история записей по дням. |
| **Entries** | Плоский список всех записей + редактор (модалка на десктопе, шторка на мобиле). Deep link `?new=1` открывает редактор сразу. |
| **Journal** | Дневник: заголовок, текст, настроение, теги; поиск и фильтры. |
| **Insights** | История AI-разборов со списком и превью, просмотр отдельного отчёта. |
| **Onboarding** | Наговорил текстом, что хочешь трекать → LLM собирает план категорий/полей → превью → применить одной транзакцией. |

## 6. Текущий Dashboard — точный разбор (это и есть объект редизайна)

Порядок блоков сверху вниз (файл `app/page.tsx`, данные — хук `useDashboard`):

1. **Заголовок**: `Dashboard.` (точка — лаймовая) + подзаголовок «Track your progress and stay motivated.»
2. **Hero-карточка**: слева большое кольцо прогресса, в центре кольца — общее число записей за всё время
   и подпись `entries`. Справа: капслок-строка «ALL GOOD, KEEP GOING», заголовок «Your recent tracking
   activity», текст «22 categories, 6 journal notes. Log something today to keep the streak alive.»
   и лаймовая кнопка «+ Log entry».
3. **Панель AI-разбора**: иконка-искры, заголовок «AI-разбор», подпись «Тренды, пропуски и корреляции
   за последние N дней», переключатель периода `7 / 30 / 90 дн.`, кнопка «Разбор периода», ссылка «История →».
   Тело панели — 4 состояния: idle (подсказка), loading (пульсирующая точка + «Анализирую период…
   это может занять до пары минут»), error (текст + Retry), ready (markdown-отчёт + строка
   «Период: N дн. · Модель: …»).
4. **KPI-ряд**: три одинаковые плитки-ссылки — `Categories 22`, `Entries 100`, `Journal 6`.
5. **Recent activity**: список последних 5 записей. Каждая строка: иконка календаря, «Entry #123»,
   дата, справа «N values» и ссылка «View». Пустое состояние — «Nothing here yet» + «Create first entry».
6. **Quick actions**: три плитки — «Add category», «Log entry», «Write journal».

### Данные, которыми экран реально располагает

Хук грузит ровно три запроса параллельно: `GET /categories`, `GET /entries` (весь список),
`GET /journal?limit=5` (берётся только `total`). Из них считаются:
`categoriesCount`, `entriesCount` (длина полного списка), `journalCount` (тотал дневника),
`recentEntries` (5 последних, сортировка `entry_date desc, id desc`).
Кольцо: `min(entriesCount / 10, 1)`.

### Честный список проблем текущего экрана

Это не жалобы, а вход для редизайна:

- **Кольцо врёт.** Оно показывает не прогресс, а `всего записей / 10`. При 100 записях оно навсегда
  заполнено на 100 % и перестаёт нести информацию.
- **KPI бесполезны как метрики.** «Categories 22 / Entries 100 / Journal 6» — это счётчики строк в БД
  за всё время. Они не отвечают ни на один вопрос, который задаёт человек, открывая трекер.
- **Нет ни одного среза «сейчас».** Экран ничего не говорит про сегодня, эту неделю, динамику,
  что просело, где серия, что пропущено — хотя `/table` и стрики всё это позволяют посчитать.
- **Нет самих привычек.** Дашборд не показывает ни одной категории по имени. Пользователь трекает
  22 категории, а видит цифру «22».
- **«Entry #123 · 5 values»** — техническое представление. Человек не помнит, что такое запись №123.
  Ни имени категории, ни значения, ни единицы.
- **Дублирование действий.** «Log entry» присутствует и в hero, и в quick actions; KPI-плитки и
  quick actions ведут почти в одни и те же места.
- **Языковая каша.** Интерфейс английский, AI-панель и её тексты — русские.
- **Статичная похвала.** «ALL GOOD, KEEP GOING» показывается всегда, независимо от того, есть ли записи
  сегодня — то есть это декорация, а не обратная связь.
- **AI-панель занимает премиальное место**, но в idle-состоянии это просто пустой прямоугольник
  с одной строкой текста; и она физически может «раздуться» на пол-экрана, когда придёт отчёт.
- **Вертикальная простыня.** Шесть блоков в одну колонку на широком экране, огромные пустоты по бокам
  плиток; на 2000 px ширины плотность информации крайне низкая.

## 7. Дизайн-система «Lime Tech» (обязательна к соблюдению)

Утверждена пользователем 2026-07-22, канон для всех клиентов.

### Палитра

| Токен | Значение |
|---|---|
| background | `#090909` |
| surface | `#141414` |
| card (elevated) | `#1A1A1A` |
| primary (lime) | `#B8FF36` |
| secondary green | `#69E76A` |
| text primary | `#FFFFFF` |
| text secondary | `#A3A3A3` |
| text disabled | `#666666` |
| success | `#4ADE80` |
| warning | `#FACC15` |
| danger | `#EF4444` |
| info | `#60A5FA` |

Палитра серий для графиков на тёмной поверхности (проверена на контраст): `#65a30d`, `#0284c7`, `#b45309`, `#9333ea`.

### Стиль

- Dark UI, glass + matte, скругления 20–28 px, много воздуха, минимум градиентов,
  без декоративных иллюстраций, без emoji в интерфейсе.
- Типографика: Inter (web) / SF Pro Display (iOS).
  H1 36 Bold · Section 22 Semibold · Card 18 Medium · Body 16 Regular · Caption 13 Medium.
- Иконки: Lucide (web) / SF Symbols (iOS), stroke 2 px.
- Акцент лайм — только на активном табе, primary-кнопках, прогресс-кольцах и свечении при завершении.
  Лайм не должен быть заливкой больших площадей.
- Числа — `tabular-nums`.

### Паттерны и состояния

- Loading — тонкое неоновое кольцо/пульс, не спиннер.
- Empty state — одна иконка, одна фраза, одна кнопка.
- Error — текст + Retry.
- Анимации: подъём карточек при касании 2–4 px, дорисовка колец 400–600 мс, fade+slide на смене вкладок,
  постепенная анимация графиков. Живой, но спокойный интерфейс.
- Мобильная версия — отдельный shell `/m` с нижним tab bar; минимальная зона тапа 44 px.
  Всё, что придумываем для дашборда, должно иметь внятную мобильную раскладку в одну колонку.

## 8. Технические ограничения реализации

- Next.js App Router, клиентские компоненты (`'use client'`), TypeScript strict, **`any` запрещён**.
- Tailwind-классы поверх токенов темы (`bg-card`, `text-text-secondary`, `text-lime`, `border-white/5` и т. д.).
- Иконки — только `lucide-react`.
- Логика экрана обязана жить в хуке (`hooks/useDashboard.ts`), а чистые вычисления — в `lib/*.ts`
  с юнит-тестами: у десктопа и `/m` общая логика и разная разметка. Любой новый расчёт для дашборда —
  это чистая функция в `lib/` + тест (в проекте TDD обязательна для бизнес-логики).
- Дополнительные запросы допустимы, но экран уже делает 3 параллельных вызова; `GET /entries`
  тянет весь список без пагинации. `GET /table?date_from&date_to` — один вызов на любой период до года,
  это самый дешёвый источник для трендов/хитмапов.
- Стрики запрашиваются по одной категории за раз (`GET /categories/{id}/streak`) — N запросов на N категорий,
  массового эндпоинта нет.
- AI-разбор — тяжёлая синхронная операция (до пары минут), у неё обязаны быть честные состояния.

## 9. Что мы хотим получить от редизайна

Задача: **переработать Dashboard так, чтобы он отвечал на вопросы, ради которых человек его открывает.**

Открывая экран, пользователь хочет понять примерно следующее:
1. Что у меня с сегодняшним днём — что уже отмечено, что ещё нет.
2. Как идёт неделя/месяц по ключевым привычкам — растёт, падает, стоит.
3. Где серия, которую жалко прервать, и где серия уже сорвана.
4. Что просело / что выпало из внимания.
5. Что мне сделать прямо сейчас одним тапом.
6. Что сказал последний AI-разбор.

Ожидаемый результат обращения:

- Структура экрана: список блоков сверху вниз, зачем каждый нужен и на какой вопрос отвечает.
- Приоритизация: что убрать, что оставить, что объединить.
- Сетка/раскладка для широкого экрана (сейчас всё в одну колонку) **и** для мобильного `/m`.
- Для каждого блока — какими именно данными из §3 он наполняется, и честная пометка,
  если блок требует того, чего в §4 нет (тогда — что именно нужно добавить в backend).
- Конкретные тексты/лейблы вместо нынешних технических («Entry #123 · 5 values»).
- Вариант поведения при малом объёме данных (0–3 категории, нет записей) и при большом (22 категории, годы истории).
- Всё в рамках дизайн-системы §7 — тёмная тема, лайм как единственный акцент, без иллюстраций и emoji.

Отдельно приветствуется: предложение, чем честно заменить кольцо прогресса, раз целей в модели нет —
либо какая минимальная доработка модели данных (например, `target` на поле) даст максимум смысла на экране.

Язык интерфейса: сейчас смешанный. Считаем допустимым предложить единый язык — укажите, какой и почему.
