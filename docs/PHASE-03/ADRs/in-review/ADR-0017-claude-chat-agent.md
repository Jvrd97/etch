# ADR-0017: Многоходовой чат с Claude внутри habit_tracker_ai

## Status

Принято (2026-08-30) — in-review. Разворачивает решения [[ADR-0005]] и [[ADR-0006]] на четвёртый юзкейс LLM-слоя; ни одно из них не отменяет.

## Context

В приложении три юзкейса LLM, и все три одноходовые: инсайты, онбординг категорий, разбор дня. Транспорт — `LLMClient.generate(prompt) -> str` (`app/llm/client.py`), чистая функция без состояния. CLI-бэкенд `CliInsightsClient` (`app/llm/cli.py`) поднимает `claude -p --output-format text` на каждый вызов и передаёт промпт через stdin. API-бэкенд шлёт `messages=[{"role": "user", ...}]` — список ровно из одного элемента. Ремонтный заход `generate_with_repair` (`app/llm/plan_flow.py`) уже упирается в это: чтобы попросить исправить ответ, он пересылает весь базовый промпт заново, потому что продолжить разговор нечем. `session_id` в `app/` не встречается нигде, таблицы диалога нет, стрима нет.

Одновременно принято решение слить в это приложение personal-os: план дня, недели, итоги, вердикт «день выигран», тренировки, цели переезжают в Postgres, а `plan_server.py` с кнопкой «Сделать план на завтра» уходит. Эта кнопка сегодня запускает `claude -p --permission-mode acceptEdits` в каталоге репозитория, и агент правит файлы дня напрямую — это единственный способ, которым день закрывался без разговора. Чат в вебе должен заменить и её, и разговорные части `/day-open` и `/day-close`. То есть чат — не украшение поверх инсайтов, а несущий интерфейс дня.

Ограничения, в которых это строится. Первое: бэкендов два, и оба обязаны работать — именно этим [[ADR-0005]] п.4 и [[ADR-0006]] обосновали отказ от native tool use Anthropic, и это ограничение в силе. Второе: VPS доступен только через Tailscale, публичного входа нет, вебхуки невозможны, аутентификация — один статический `X-API-Key` (`app/core/auth.py`), пользователей как сущности не существует ни в одной из десяти таблиц. Третье: prod поднят под `gunicorn --workers 2 --timeout 180`, и таймаут воркера намеренно держится выше `LLM_TIMEOUT_SECONDS = 120`. Четвёртое: правило проекта — бизнес-логика не зовёт LLM напрямую, единственный импорт `anthropic` живёт в `app/llm/client.py`, и инвариант проверяем грепом.

Пятое обстоятельство обнаружено измерением, а не чтением кода, и оно меняет форму решения. `claude -p`, запущенный как есть, загружает пользовательские настройки: глобальный `~/.claude/CLAUDE.md`, `SessionStart`-хуки, MCP-серверы, скиллы. В prod-компоузе хостовый `~/.claude` смонтирован в контейнер, то есть это уже происходит на сервере. Замер на CLI 2.1.250:

| Запуск | input+cache_creation первого хода |
|---|---|
| `claude -p` как в `cli.py` сейчас | 52 555 токенов |
| `claude -p --tools ""` | 32 775 токенов |
| `claude -p --tools "" --setting-sources "" --system-prompt "…"` | **282 токена** |

В прогоне без изоляции модель попыталась отработать личный скилл `/set` и написала об этом в ответе пользователю. Для отчёта раз в день это дорогая странность; для чата на десятки ходов это и стоимость подписки, и утечка личной конфигурации в каждый запрос, и непредсказуемое поведение.

Шестое: возобновление сессии CLI проверено вживую. `--session-id <uuid>` принимает наш собственный UUID, `--resume <uuid>` из нового процесса корректно достаёт предыдущие ходы (контрольный ответ «4271», «ЯКОРЬ-77»), второй ход читает 21 685 токенов из кеша вместо пересчёта. Но хранится сессия файлом `~/.claude/projects/<слаг-cwd>/<session_id>.jsonl` — на диске хоста, вне Postgres, вне `deploy/backup.sh`, и ключом является рабочий каталог процесса.

## Decision

Чат получает **собственную историю сообщений в Postgres как источник истины**, CLI-сессию — только как подсказку для дешёвого продолжения, **стрим по SSE**, **ограниченную карточку дня в промпте плюс белый список именованных выборок** вместо «всего в промпт» и **право предлагать, но не право писать**: любая запись идёт планом-данными через подтверждение человека, тем же транзакционным путём, что и разбор дня.

Разворачиваю по пунктам.

**1. Память диалога — своя таблица, resume поверх неё.** `chat_messages` хранит весь диалог. `chat_conversations.cli_session_id` — необязательная подсказка: если она есть, бэкенд `cli`, cwd совпадает и `context_version` не менялся, следующий ход уходит как `--resume <uuid>` с одним новым сообщением. Иначе диалог реплеится из таблицы одним промптом. Одно поведение снаружи, две стратегии внутри — это и есть глубокий модуль: снаружи `respond(conversation, text)`, внутри выбор транспорта.

**2. Транспорт расширяется вторым методом, а не переписыванием первого.** `LLMClient.generate(prompt) -> str` остаётся дословно: на нём стоят три работающих юзкейса и граница моков в четырёх файлах тестов. Рядом появляется `ChatLLMClient.stream_turn(...) -> AsyncIterator[ChatChunk]`. CLI реализует его через `--output-format stream-json --include-partial-messages` (проверено: события `stream_event/content_block_delta` с `text_delta`, финальный `result` с `session_id` и `usage`); API — через `messages.stream` с полным списком сообщений.

**3. Каждый вызов CLI изолирован от личной конфигурации.** Обязательный набор флагов: `--tools ""` (модель ничего не исполняет), `--setting-sources ""` (ни хуков, ни глобального CLAUDE.md, ни чужих MCP), `--system-prompt <промпт чата>`, `--session-id`/`--resume`, `--output-format stream-json`. `CLAUDE_CONFIG_DIR` для этих процессов указывает на отдельный том `/data/claude-chat`, cwd фиксирован пустым каталогом `/data/claude-chat/workspace`. Аутентификация при этом обязана идти через `CLAUDE_CODE_OAUTH_TOKEN` — монтированный `~/.claude.json` в изолированном конфиге не читается. Это предусловие деплоя, а не деталь.

**4. Стрим — SSE поверх обычного POST.** `POST /api/v1/chat/conversations/{id}/messages` отвечает `text/event-stream` с событиями `delta`, `plan`, `usage`, `done`, `error`. Ответ пишется в БД из `finally` генератора, поэтому обрыв соединения оставляет сообщение со статусом `interrupted` и уже полученным текстом, а не пустоту. Сессия БД не удерживается на время генерации: контекст читается, сессия закрывается, стрим идёт, для записи берётся новая — это заодно закрывает долг из `concern-charts-ai-followups.md`, где `insights` держит соединение из пула все 120 секунд.

**5. Один ход на диалог одновременно.** Параллельный `--resume` по одной сессии портит её jsonl и удваивает расход подписки. Второй POST в диалог с незакрытым ходом получает 409. Плюс глобальный потолок одновременных CLI-процессов — система однопользовательская, потолок 2.

**6. Контекст — карточка дня плюс выборка по имени.** В системный промпт первого хода кладётся ограниченная карточка: дата, план дня, отметки, якоря, задачи, дневные health-свёртки, счётчик входящих сигналов — с жёстким потолком `CHAT_CONTEXT_MAX_CHARS`. Всё остальное модель просит сама, отвечая блоком `{"need": [{"query": "...", "params": {...}}]}`. Сервер исполняет только имена из белого списка (`entries_range`, `journal_range`, `health_daily`, `streak`, `table_slice`, `day_card`), выполняет их существующим CRUD и продолжает тот же ход. Каждая выборка пишется строкой в `chat_retrievals`: имя, параметры, число строк, число символов. Без этой таблицы утверждение [[ADR-0005]] п.2 («одна точка выхода данных, легко аудитить») для чата перестаёт быть правдой, потому что контекст перестал быть фиксированным.

**7. Права на запись — три класса, и только один из них доступен чату.**

| Класс | Что это | Как проходит |
|---|---|---|
| R — чтение | карточка дня, именованные выборки | сервер исполняет сам, подтверждения нет |
| W1 — добавление без потерь | поставить отметку, записать метрику, дописать текст дня, завести задачу или челлендж | модель возвращает операцию в плане, человек подтверждает галочками, пишет существующий транзакционный apply |
| W2 — изменение и удаление | снять отметку, переписать план дня, удалить задачу, изменить категорию или поле | **невыразимо в схеме плана**, как в `CheckOp` физически нет поля `value` |

То есть на прямой вопрос «может ли чат сам ставить отметки, создавать челленджи, править план дня»: отметки и челленджи — предлагает, применяет человек одним тапом; править существующий план дня — не может вовсе, и это свойство типов, а не текста промпта. Модель, ответившая мимо инструкции, всё равно не сможет сказать слово, которого нет в схеме.

> **Уточнено 2026-08-31 в [[ADR-0021]].** Переписывание плана дня выведено из W2 в разрешённые операции: день заменяется целиком, имя операции ставит сервер по состоянию базы, отметки переносятся по кодам строк. Остальной класс W2 — снятие отметки, удаление, переименование — закрыт по-прежнему, и тест на схему это по-прежнему держит.

**8. Планы персистятся.** `chat_plans` хранит валидированный план рядом с сообщением ассистента. Сейчас `DailySummaryPlan` не сохраняется нигде — в одноходовом экране это верно, в многоходовом чате реплика «вернись к тому, что ты предлагал два хода назад» обычная, а возвращаться не к чему. Плюс без записи нельзя доказать, что применено ровно то, что было показано.

**9. Чат не пишет в `transcripts`.** Содержание уже лежит в `chat_messages`; вторая копия того же текста — ровно то дублирование, которое запрещено в других местах проекта.

### API

| Метод и путь | Что делает |
|---|---|
| `POST /api/v1/chat/conversations` | 201, `{id}`; принимает `started_on` и `kind` |
| `GET /api/v1/chat/conversations` | лента: `limit`, `archived` |
| `GET /api/v1/chat/conversations/{id}` | сообщения плюс планы |
| `POST /api/v1/chat/conversations/{id}/messages` | `text/event-stream`; 409 — ход уже идёт, 503 — бэкенда нет, 502 — сбой бэкенда |
| `POST /api/v1/chat/plans/{plan_id}/apply` | переиспользует `apply_daily_summary` и `Idempotency-Key`; коды 201/200/400/409/422 те же, что у `/daily-summary/apply` |
| `POST /api/v1/chat/plans/{plan_id}/dismiss` | 204 |

Последняя строка — не мелочь. Диалог, удалённый из приложения, но лежащий на диске сервера, делает кнопку удаления ложью.

### Границы слоёв

`app/llm/chat/`: `client.py` (`ChatLLMClient`, CLI- и API-реализации), `prompt.py` (системный промпт чата, `context_version`), `context.py` (`build_day_card`), `plan.py` (парсер `ChatPlan` поверх `plan_flow`), `retrieval.py` (белый список имён и их параметров). Исполнение выборок и запись — в `app/crud/chat.py` и существующем `app/crud/daily_summary.py`. Клиент резолвится только в `app/api/chat.py` через `app/api/deps.get_llm_client` — правило «бизнес-логика не зовёт LLM напрямую» держится, инвариант «`import anthropic` только в `app/llm/client.py`» не нарушается.

Граница моков в тестах — `ChatLLMClient.stream_turn`. Существующие четыре файла тестов, мокающие `LLMClient.generate`, не трогаются.

### Личные и медицинские данные

**Уходит в модель:** день и его отметки, тексты дневника, дневные health-свёртки (шаги, пульс покоя и то, что добавится в каталог), задачи, названия категорий и полей. Это медицинские данные по смыслу, и решение [[ADR-0005]] п.2 на них распространяется: система однопользовательская, пользователь — владелец, выход данных — одна точка.

**Не уходит:** почасовые health-корзины (только дневные свёртки и только за запрошенный диапазон), тела писем и сообщений Telegram без явного действия человека (сигнал попадает в карточку заголовком, тело — только по кнопке «разобрать это»), ключи и токены. Именно поэтому карточка дня строится сервером, а не «всё что есть за период».

**Хранится:** полная история сообщений в Postgres — иначе чат не чат. `content` не пишется в логи никогда, `error_code` машинный, `echo=False` у движка остаётся. `chat_retrievals` даёт ответ на вопрос «какие мои данные и когда покинули сервер» без чтения самих данных.

### Где проходит граница второго пользователя

Не в схеме. Новые таблицы намеренно не получают `user_id`: девять существующих его не имеют, и смешанная схема хуже однородной. Настоящая стена — бэкенд LLM: `claude -p` аутентифицируется одной подпиской Claude Code на процесс, поэтому второй пользователь означает `LLM_BACKEND=api` и ключ на пользователя, а не миграцию чата. Точка, которую надо будет тронуть в коде, ровно одна: `app/api/chat.py` берёт владельца из будущего `current_principal()`, сегодня возвращающего константу. Стоимость второго пользователя = миграция всех тринадцати таблиц + отказ от CLI-пути; эта оценка честная и её надо держать перед глазами, а не прятать за «мы заложили user_id».

## Options considered

### Память диалога

#### Вариант A: только флаги CLI (`--session-id` / `--resume`), своей таблицы нет
- **Описание**: история живёт в jsonl-файле CLI, приложение хранит только `session_id`.
- **Плюсы**: почти нет кода; кеш промпта работает идеально (замер: 21 685 токенов из кеша на втором ходу).
- **Минусы**: история вне Postgres и вне `deploy/backup.sh`; ключ — рабочий каталог процесса; API-бэкенд такого не умеет вовсе, то есть один из двух обязательных путей остаётся без чата; UI нечем нарисовать ленту после перезапуска; удалить разговор — значит ходить по файлам.
- **Отвергнут потому, что**: делает работоспособность фичи свойством файловой системы контейнера и ломает паритет бэкендов, зафиксированный [[ADR-0006]].

#### Вариант B: только своя таблица, каждый ход — новый полный промпт
- **Описание**: как `generate_with_repair` сегодня, но с полным диалогом в теле промпта.
- **Плюсы**: один механизм на оба бэкенда; полный контроль над тем, что ушло.
- **Минусы**: каждый ход платит за весь диалог заново; на CLI это ещё и повторная загрузка префикса; десятиходовый разговор становится дорогим квадратично.
- **Отвергнут потому, что**: цена растёт квадратично там, где CLI даёт линейную бесплатно.

#### Вариант C: таблица как источник истины, resume как оптимизация (выбран)
- **Плюсы**: работает на обоих бэкендах; переживает перезапуск, потерю файла сессии и смену cwd; кеш используется, когда доступен; удаление диалога — обычный `DELETE` плюс удаление файла.
- **Минусы**: две стратегии внутри одного метода, и вторую надо тестировать отдельно; расхождение «в таблице одно, в jsonl другое» возможно и требует `context_version`.
- **Выбран потому, что**: единственный вариант, при котором ни отказ CLI, ни выбор `LLM_BACKEND=api` не отнимают у пользователя историю.

### Контекст

#### Вариант A: всё в промпт
- **Отвергнут**: год записей плюс дневник — мегабайты; `build_period_context` уже упирается в потолок `MAX_JOURNAL_ENTRIES = 200`, и это одноходовый отчёт, а не разговор.

#### Вариант B: MCP-сервер с read-only тулами через `--mcp-config` + `--allowedTools`
- **Плюсы**: родной способ, CLI его поддерживает; модель сама решает, что читать.
- **Минусы**: на API-бэкенде MCP нет, паритет ломается; тулы возвращают в промпт свои определения и часть выигрыша изоляции; отдельный процесс с доступом к БД; `how-to` по CLI-бэкенду прямо предупреждает, что включённые тулы — «совсем другой профиль риска, и обёртку надо пересматривать целиком».
- **Отвергнут потому, что**: ломает ограничение двух бэкендов, ради которого [[ADR-0005]] и [[ADR-0006]] уже отказались от native tool use. Сигнал к пересмотру назван ниже.

#### Вариант C: карточка дня плюс именованные выборки по белому списку (выбран)
- **Плюсы**: одинаково работает на обоих бэкендах; белый список — аудируемая граница; каждая выборка оставляет след в `chat_retrievals`; никакого второго процесса.
- **Минусы**: свой мини-протокол, который надо парсить и чинить (переиспользуется `plan_flow`); лишний заход к модели, когда карточки не хватило; список имён придётся расширять руками.
- **Выбран потому, что**: даёт динамический контекст, не отдавая модели ни исполнения, ни паритета бэкендов.

### Право записи

#### Вариант A: чат пишет сам (тулы записи, `--permission-mode acceptEdits`)
- **Описание**: то, что personal-os делает сегодня кнопкой «Сделать план на завтра».
- **Плюсы**: один шаг вместо двух; день закрывается без разговора.
- **Минусы**: неверный ответ модели молча уничтожает данные дня; на VPS с медданными аудита нет; `CheckOp`-инвариант («снять галку нечем») перестаёт существовать.
- **Отвергнут потому, что**: ровно этот механизм и делает нынешний handoff непроверяемым — план дня меняется, и никто не знает кем и почему.

#### Вариант B: план-данные плюс подтверждение человека (выбран)
- **Плюсы**: переиспользует готовый транзакционный `apply_daily_summary` с `Idempotency-Key`; разрушительная операция невыразима в типах, а не запрещена текстом; человек видит, что именно применяет.
- **Минусы**: два тапа вместо одного; «закрой день сам, я сплю» — не работает; часть смысла кнопки personal-os теряется.
- **Выбран потому, что**: это единственный вариант, где ошибка модели стоит одного невыполненного действия, а не потерянного дня.

#### Вариант C: автоприменение отметок с окном отмены
- **Отвергнут на этот срез**: окно отмены требует истории версий отметки, которой в схеме дня ещё нет. Вернуться к этому можно отдельным ADR, когда таблицы дня приедут.

### Стрим

#### Вариант A: WebSocket — отвергнут: держит соединение через Tailscale и gunicorn ради одного пользователя, а выигрыша над SSE в одностороннем потоке нет.
#### Вариант B: опрос по таймеру — отвергнут: ответ появляется рывками, а БД получает лишние записи на каждый чанк.
#### Вариант C: SSE поверх POST (выбран) — обычный HTTP, работает через прокси Next.js, переживает `--timeout` при поднятом до 300 значении, читается из фронта через `fetch` + `ReadableStream`.

## Consequences

### Что становится проще
- День закрывается разговором, а не заполнением трёх экранов: `/today`, `/daily-summary` и `/journal` получают общий вход.
- Ремонтный заход перестаёт быть отдельным механизмом: в диалоге исправление — это просто следующий ход.
- Расход подписки становится видимым: `input_tokens`, `output_tokens`, `cache_read_tokens` пишутся на каждое сообщение, а не теряются.
- Утечка личной конфигурации в LLM-запросы закрывается для всех четырёх юзкейсов сразу, если те же флаги изоляции применить и к `generate`.

### Что становится сложнее
- Транспорт перестаёт быть чистой функцией: у `stream_turn` есть состояние (сессия), и тесты обязаны покрыть обе стратегии — resume и реплей.
- Появляется конкурентность там, где её не было: блокировка хода, потолок процессов, запись из `finally` на обрыве.
- Отладка усложняется: ошибка теперь может быть в парсинге потока, в возобновлении сессии, в выборке по имени или в плане — четыре места вместо одного.
- Prod получает предусловие, которого не было: `CLAUDE_CODE_OAUTH_TOKEN` становится обязательным, `gunicorn --timeout` поднимается до 300, появляется том `/data/claude-chat`.

### Какие риски приняты
- CLI ходит по подписке Claude Code. `how-to` прямо говорит, что это для редких тяжёлых запросов, а не для трафика. Чат — десятки ходов в день. Первые 429 означают переход на `LLM_BACKEND=api` и реальные деньги.
- Каждый ход — новый процесс Node: секунды на старт и заметная память при двух воркерах.
- `--setting-sources ""` проверен на CLI 2.1.250 и в общем списке опций описан скупо. Обновление CLI может изменить поведение. Компенсация — смоук-тест, валящий сборку, если первый ход снова весит десятки тысяч токенов.
- `--resume` привязан к cwd и к файлу на диске: любая смена рабочего каталога процесса тихо обнуляет кеш. Компенсация — `cli_cwd` в таблице и сверка перед resume.
- Расхождение канона с кодом продолжается: [[ADR-0006]] постановил ввести LangChain, в `pyproject.toml` его нет, и этот ADR тоже строится без него. Третий юзкейс подряд живёт по отвергнутому варианту B — это надо закрыть отдельным ADR, а не молчанием.

### Чего мы здесь не решаем
- Операции чата над планом дня, тренировкой и вердиктом: таблиц дня ещё нет, это отдельный ADR слияния personal-os.
- Голосовой ввод в чат: `useSpeechRecognition` существует, но связка — отдельный срез.
- Перестановка табов и десктоп-навигации: пять слотов заняты, чат в первом срезе живёт в «More».
- Класс W2 (изменение и удаление) целиком. *(Позже открыт на одну операцию — [[ADR-0021]].)*
- Множественность пользователей: граница описана, работа не начата.

## Reversal cost

**Medium (1-2 недели).** Откат к одноходовым экранам: снять роутер `chat`, удалить четыре таблицы вниз по миграции, вернуть `ChatLLMClient`-реализации в небытие. `LLMClient.generate` не тронут, три существующих юзкейса не заметят. Дороже другое — история диалогов станет мёртвой, если фичу снимут после месяца использования; поэтому таблицы и стоит держать в Postgres, а не в файлах.

Сигналы к пересмотру: (1) rate limits подписки на чате — переход на API-бэкенд; (2) native tool use становится доступен на обоих путях — тогда белый список выборок стоит заменить настоящими тулами отдельным ADR; (3) первый случай, когда человек применил план, не читая — значит подтверждение стало ритуалом и защиты не даёт, надо менять форму, а не отменять правило.

## Notes

Проверяемость решений — таблица «как понять, что сделано правильно»:

| Решение | Проверка |
|---|---|
| Изоляция от личной конфигурации | `input_tokens + cache_creation_input_tokens` первого хода < 1000; в ответе нет следов личных скиллов и хуков |
| Своя история как источник истины | `rm` файла сессии CLI → следующий ход всё ещё правильно отвечает на вопрос про первый ход |
| Resume работает | второй ход имеет `cache_read_tokens > 0` и `latency_ms` меньше первого |
| Стрим | первый `delta` приходит раньше двух секунд от старта; ответ виден по кускам, а не целиком |
| Обрыв не теряет ответ | закрыть вкладку на середине → перезагрузка показывает частичный текст со статусом `interrupted` |
| Один ход на диалог | два одновременных POST → второй отвечает 409, второй процесс CLI не стартует |
| Карточка дня ограничена | день с 50 записями и длинным дневником не превышает `CHAT_CONTEXT_MAX_CHARS` |
| Выборки аудируемы | «сравни сон за прошлую неделю с позапрошлой» → две строки в `chat_retrievals` с верными `row_count` |
| Белый список закрыт | имя вне списка не доходит до БД и возвращается модели как отказ |
| W2 невыразим | в JSON-схеме `ChatPlan` нет операции снятия отметки, удаления и переименования — проверяется тестом на схему, не на промпт. Перезапись плана дня из этого списка выведена [[ADR-0021]] |
| Применение идемпотентно | повторный тап по «применить» отвечает 200 и не пишет вторых записей |
| Удаление полное | `DELETE` → нет строк в четырёх таблицах и нет jsonl-файла сессии |
| Граница слоёв | `grep -r "import anthropic" app/` даёт ровно один файл; `grep -r "resolve_llm_client" app/` — только `deps.py` |
