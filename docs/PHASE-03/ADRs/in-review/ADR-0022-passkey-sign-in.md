# ADR-0022: Passkey — второй способ получить ту же сессию браузера

## Status

Принято (2026-10-25) — in-review. Дополняет сессию браузера из `#109`, ничего в ней не меняя.

## Context

Браузер входит одним способом: на `/login` вводится `API_KEY`, бэкенд меняет его на подписанную куку `habit_session`. Ключ — 64 шестнадцатеричных символа, на iPhone его вставляют руками. Пользователь попросил входить с телефона по Face ID.

WebAuthn (стандарт, на котором стоят passkey) привязывает ключ к доменному имени — RP ID — и к origin страницы. Он не работает на IP-адресе и вне безопасного контекста. Прод сейчас открывается по `http://100.121.220.42:3000`, и там passkey не включит ни один браузер. Работают два адреса: HTTPS-имя Tailscale (`https://<машина>.<tailnet>.ts.net` через `tailscale serve`) и `http://localhost` для разработки.

## Decision

1. **Passkey выдаёт ту же куку `habit_session`, что и вход по ключу.** Периметр (`require_api_key`) смотрит на куку, а не на то, чем её получили. Клиенты с `X-API-Key` (iOS, mac-агент, скиллы) ничего не замечают.
2. **Учётных записей нет.** Пользователь один (ADR-0003), поэтому у таблицы `webauthn_credential` нет `user_id`, а `user.id` WebAuthn — константа. Ключ discoverable (resident key, user verification required): на входе имя не спрашивается, Safari сам предлагает passkey в окне Face ID.
3. **Вызов (challenge) живёт в подписанной куке, а не в таблице.** `habit_passkey_challenge` — `HttpOnly`, `SameSite=Strict`, срок 5 минут, своя соль подписи, назначение (`register`/`login`) внутри. Сервер между двумя запросами церемонии ничего не хранит — так же, как не хранит сессий.
4. **Повтор ответа отбивается по времени последнего использования ключа.** Счётчик подписей у синхронизируемых passkey (iCloud Keychain) всегда ноль и повтор не ловит. Поэтому вход отклоняется, если вызов выпущен не позже `last_used_at` этого ключа. Откат ненулевого счётчика отклоняется отдельно (проверка `py_webauthn`).
5. **Регистрация, список и удаление — только для вошедшего клиента.** Вход по passkey открыт, как `POST /auth/session`.
6. **Пока RP ID и origin не заданы, passkey выключен.** `GET /auth/passkey/status` отвечает `enabled: false`, ручки церемоний — 503, интерфейс кнопок не рисует. Половина пары, IP-адрес в `WEBAUTHN_RP_ID` и origin вне RP ID роняют старт с сообщением, называющим переменную.
7. **Проверку WebAuthn делает `py_webauthn`** (`webauthn` на PyPI). Подписи, CBOR, COSE-ключи и разбор `authenticatorData` своими руками не пишутся. На фронте новых зависимостей нет: base64url и перевод параметров — в `lib/passkey.ts`.

## Consequences

- Включение на проде — работа человека: `tailscale serve`, три переменные, перезапуск (`habit-tracker/docs/passkey.md`). До этого всё работает как раньше.
- Passkey привязан к имени. Сменилось имя машины или tailnet — старые ключи бесполезны, их удаляют в настройках и добавляют заново.
- По HTTPS-имени кука сессии может быть `Secure`. Тогда вход по `http://<IP>:3000` перестаёт сохранять сессию — адрес по IP становится лишним.
- Два одновременных входа одним ключом: второй получит отказ, потому что первый сдвинул `last_used_at`. Повторное нажатие проходит.
- Удаление ключа не гасит сессии, уже открытые им: отзыв одной сессии по-прежнему невозможен, гасит все разом смена `SESSION_SECRET`.
- В нативном iOS-приложении passkey нет: ему нужны Associated Domains с файлом AASA, который Apple забирает из публичного интернета, а хост только в tailnet ей не виден. Там будет Face ID на элементе Keychain с ключом — отдельный тикет iOS.

## Notes

Отвергнуто: таблица вызовов. Она дала бы одноразовость вызова в чистом виде, но требует уборки протухших строк и ещё одного места, где живёт состояние входа. Правило «вызов моложе последнего использования ключа» закрывает повтор без неё.
