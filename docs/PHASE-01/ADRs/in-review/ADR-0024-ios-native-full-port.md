# ADR-0024: iOS-приложение — полный нативный клиент, редкие экраны тоже на SwiftUI

## Status

Принято владельцем 2026-10-29 (тикет [#216], вариант A) — in-review. Заменяет два пункта
ADR-0020: в A1 — сужение назначения iOS-приложения до насоса HealthKit, в A5 — отказ от
нативных экранов здоровья. Остальной текст A1 (HealthKit читает только iPhone) и A5 (десктопная
пара `/health` + `/m/health`) действует.

## Context

ADR-0020 (2026-08-30) сузил iOS-приложение до насоса HealthKit: разрешения, чтение, отправка,
состояние синка. Экраны здоровья он оставил вебу со ссылкой на решение человека «копии интерфейса
в нативном приложении не делаем».

С тех пор решение перевернулось на практике. Тикеты [#208]–[#214] и волны роя 1–5 сделали
нативными ежедневное ядро: Today, Day, Chat, Health-синк, Неделю, Быстрые отметки, Добавки,
итог дня, а также Dashboard, Categories, Table, History, Journal, Insights, Settings. 2026-10-25
владелец попросил «в идеале полный порт на Swift», 2026-10-29 — «доделывай приложение на iOS
полностью». Вне приложения остались редкие экраны: Goals, Life, Roles, Onboarding и метрики
здоровья.

Тикет [#216] сравнил три варианта для редких экранов (см. Options considered). Вариант B
(`WKWebView` на `/m/*`) упирался в куку сессии: кука по умолчанию `Secure`, а прод работает по
http внутри Tailscale. Без HTTPS из [#205] вход в WebView не работает.

## Decision

Одной строкой: **iOS-приложение — полный клиент системы: каждый экран мобильного веба получает
нативного двойника на SwiftUI, WebView и ссылок «открыть в Safari» в приложении нет.**

**D1. Назначение iOS-приложения (заменяет сужение из ADR-0020 A1).** Приложение — насос
HealthKit и полный клиент: всё, что умеет мобильный веб `/m/*`, делается и в приложении. Ограничение
A1 о том, что HealthKit читает только iPhone, остаётся: агент на macOS данные здоровья по-прежнему
не читает.

**D2. Экраны здоровья нативны (заменяет отказ из ADR-0020 A5).** Метрики здоровья рисует вкладка
Health приложения (тикет [#268]). Десктопная пара `/health` + `/m/health` остаётся, десктоп
по-прежнему первичен для разбора. Арифметики на телефоне не появляется: экран читает
`GET /health/metrics`, инвариант A2 не меняется.

**D3. Источник поведения — веб.** Нативный экран повторяет поведение компонента мобильного веба,
а не придумывает своё: те же действия, те же состояния, тот же текст пустого экрана. Тикет
нативного экрана называет компонент-источник (для Goals — `components/goals/GoalsBoard.tsx`),
а XCTest на view model повторяет случаи из теста компонента. Действие, которого нет в вебе,
в приложение не добавляется без отдельного тикета, и наоборот.

**D4. Новая веб-фича с интерфейсом получает iOS-двойника.** Тикет веб-экрана либо сам включает
слой `ios/`, либо ссылается на парный iOS-тикет. Исключения прежние: web-only фичи из
дополнения к ADR-0004 (голосовой конструктор категорий) и десктопные экраны разбора.

**D5. Разрезка.** Тикет [#216] — этот ADR и экран Goals. Life — [#265], Roles — [#266],
Onboarding — [#267], метрики здоровья — [#268]. Passkeys на iOS не переносятся: вход в
приложение — ключ API и Face ID ([#214]).

## Options considered

### Вариант A: всё нативно — **выбран**

Каждый экран мобильного веба переписан на SwiftUI. Плюсы: единый вид и жесты, работа офлайн
через общий кэш чтения и очередь (ADR-0002), нет зависимости от куки и HTTPS. Цена: каждая
будущая веб-фича с интерфейсом стоит вдвое, паритет может разойтись незаметно. Цену ограничивают
D3 и D4.

### Вариант B: ежедневное ядро нативно, редкие экраны — `WKWebView` на `/m/*`

Дешевле на старте. Отвергнут: вход в WebView требует куку сессии, а кука `Secure` не ставится по
http — нужен HTTPS Tailscale из [#205]. Ещё одна причина: внутри приложения появляются два вида
интерфейса, и WebView не работает без сети.

### Вариант C: редкие экраны только в вебе, в приложении — ссылка «открыть в Safari»

Самый дешёвый. Отвергнут прямым решением владельца «доделывай приложение на iOS полностью».

## Consequences

### Что становится проще

- Человек живёт в одном приложении на телефоне; браузер нужен только на десктопе.
- Редкие экраны работают офлайн тем же путём, что и ежедневные.

### Что становится сложнее

- Каждая веб-фича с интерфейсом стоит двух реализаций (D4).
- Паритет держится дисциплиной тикетов и зеркальными тестами (D3), автоматической сверки нет.

### Какие риски приняли

- Паритет расходится незаметно: веб-тикет меняет поведение, iOS-двойник не обновлён. Сигнал —
  ревью веб-тикета без строки об iOS-слое.

## Reversal cost

**Низкая для ещё не сделанных экранов, средняя для сделанных.** Отказ от варианта A для будущих
экранов — это вариант B или C, бэкенд не меняется. Уже сделанные нативные экраны можно не
удалять: они работают на тех же эндпоинтах.

## Как понять, что сделано правильно

| Решение | Проверка |
|---|---|
| D1, D5 | Каждый пункт навигации мобильного веба имеет экран во вкладках или в «Ещё» приложения. |
| D2 | Вкладка Health показывает метрики с сервера; в `ios/` нет сложения семплов. |
| D3 | Тест view model нативного экрана покрывает случаи теста веб-компонента-источника. |
| D4 | У веб-тикета с интерфейсом есть слой `ios/` или ссылка на iOS-тикет. |
