# ADR-0006: Обобщение LLM-слоя под второй юзкейс — LangChain как orchestration

## Status

Accepted (грилл 2026-07-25). Уточняет пункт 1 [[ADR-0005]] («голый SDK, абстракция со вторым юзкейсом»). Ссылается на дополнение к [[ADR-0004]] от 2026-07-25.

## Context

[[ADR-0005]] зафиксировал LLM-слой на голом `anthropic-sdk` без LangChain с явной оговоркой: фреймворк вводим, «когда появится второй юзкейс и реальная потребность в абстракции». Первый юзкейс — «инсайты по кнопке»: один провайдер, один промпт, `InsightsClient` знал и про транспорт, и про смысл разбора.

Второй юзкейс наступил — голосовой конструктор категорий (`PRD-voice-category-builder`). Он делит с инсайтами транспорт (тот же вызов модели, те же два бэкенда), но всё остальное у него своё: другой промпт, другой парсинг (JSON-в-тексте + строгая Pydantic-валидация с одним ремонтным заходом), другая доменная валидация результата. При этом `InsightsClient` по имени и по API привязан к инсайтам — второй юзкейс не может переиспользовать его, не потащив за собой «insights» в названиях и сигнатурах.

Два обстоятельства ограничивают форму абстракции. Первое: бэкендов два — `anthropic-sdk` (API) и `claude -p` (CLI через subprocess, дополнение #26 к ADR-0005), выбор через `LLM_BACKEND`. Оба обязаны обслуживать оба юзкейса — именно это в PRD названо причиной отказа от native tool use Anthropic (он есть только на API-пути и убил бы бесплатный CLI-путь на подписке Claude Code). Второе: правила проекта прямо называют LangChain и требуют изолированный orchestration-слой; ADR-0005 отложил его только до появления второго юзкейса — теперь это условие выполнено.

## Decision

Вводим LangChain как orchestration-слой над обоими бэкендами и разделяем `app/llm/` на транспорт и специфику юзкейса.

Транспорт становится нейтральным: единый интерфейс уровня `LLMClient.generate(prompt) -> str`, за которым прячутся оба бэкенда. API-бэкенд ложится на штатную LangChain-интеграцию Anthropic; CLI-бэкенд (`claude -p`) оборачивается в кастомный LangChain LLM поверх subprocess, поскольку из коробки LangChain про CLI-путь не знает. `InsightsClient` в его текущем виде уходит — он перестаёт быть про insights.

Специфика каждого юзкейса живёт рядом, отдельными модулями: свой промпт-темплейт, свой парсер (для голосового конструктора — JSON-в-тексте + Pydantic + один ремонтный заход), своя доменная валидация. Инсайты и голосовой конструктор собирают свою цепочку из общего транспорта и собственной обвязки, а не наследуют один божеский клиент. Structured output остаётся текстовым (JSON в ответе), native tool use не используется — ограничение двух бэкендов из ADR-0005 в силе, LangChain его не снимает.

## Options considered

### Option A: LangChain как orchestration-слой (selected)
- **Description**: единый `LLMClient.generate` над обоими бэкендами на LangChain (штатная интеграция для API, кастомный LLM-wrapper для CLI); промпт/парсинг/валидация каждого юзкейса — отдельные модули поверх общего транспорта.
- **Pros**: выполняет условие ADR-0005 (второй юзкейс наступил) и требование правил проекта; специфика юзкейса развязана с транспортом — третий юзкейс не трогает первые два; готовые примитивы цепочек/парсеров/ретраев вместо самописных.
- **Cons**: CLI-путь требует кастомного LLM-wrapper (LangChain его не знает); плюс зависимость с своей магией поверх ровно двух пока юзкейсов.
- **Selected because**: явно выбрано в грилле; условие отсрочки из ADR-0005 выполнено, а правила проекта называют LangChain каноном для orchestration.

### Option B: нейтральный `LLMClient` на голом SDK/CLI, без LangChain
- **Description**: переименовать `InsightsClient` в нейтральный `LLMClient.generate(prompt) -> str` на голом SDK/CLI, специфику юзкейса вынести в соседние модули — но без фреймворка.
- **Pros**: минимум зависимостей и магии (линия ADR-0005); оба юзкейса — простой `prompt -> текст`, цепочек LangChain пока не требуют.
- **Cons**: расходится с правилами проекта, называющими LangChain; при третьем-четвёртом юзкейсе всё равно придётся вводить фреймворк — отложенная та же работа.
- **Rejected because**: грилл выбрал ввести фреймворк сейчас, на явно наступившем втором юзкейсе, а не откладывать ещё раз.

### Option C: оставить `InsightsClient`, второй юзкейс дописать рядом копипастой
- **Description**: не трогать существующий клиент, для голосового конструктора завести параллельный клиент с продублированным транспортом.
- **Pros**: не трогает работающий код инсайтов, нулевой риск регресса первого юзкейса.
- **Cons**: два экземпляра логики выбора бэкенда и вызова модели; «insights» в названиях остаётся семантическим мусором; третий юзкейс плодит третью копию.
- **Rejected because**: дублирование транспорта — ровно тот долг, который ADR-0005 обещал закрыть на втором юзкейсе.

## Consequences

### What becomes easier
- Третий юзкейс собирается из готового транспорта плюс своя обвязка, не трогая инсайты и голосовой конструктор.
- Промпт, парсер и валидация каждого юзкейса читаются в своём модуле, а не внутри разросшегося клиента.
- Ретраи/парсеры/цепочки берутся из LangChain, а не пишутся заново под каждый юзкейс.

### What becomes harder
- CLI-бэкенд (`claude -p`) надо самим обернуть в LangChain-совместимый LLM — из коробки его нет; этот wrapper теперь на нашей поддержке.
- Плюс зависимость со своим жизненным циклом и версионной магией поверх пока лишь двух юзкейсов.
- Отладка ошибки модели идёт через слой абстракции LangChain, а не по прямому вызову SDK.

### What new risks did we accept
- Расхождение поведения двух бэкендов (API vs CLI) теперь маскируется общим интерфейсом — легче не заметить, что CLI склеивает system-промпт в user (известное расхождение из ADR-0005).
- Обновление LangChain может сломать кастомный CLI-wrapper — точка хрупкости на стыке фреймворка и subprocess.

### What we're explicitly NOT solving (yet)
- Native tool use / structured outputs Anthropic — остаются вне игры, пока оба бэкенда обязаны работать (ADR-0005).
- Мульти-провайдерность (не-Anthropic модели) — интерфейс нейтральный, но второго провайдера не вводим.
- Стриминг ответов — оба юзкейса синхронные `prompt -> текст`.

## Reversal cost

**Medium** (1-2 недели). Интерфейс `LLMClient.generate` изолирует вызовы, так что снять LangChain и вернуться на голый SDK/CLI можно без изменения контрактов юзкейсов — но переписать оба бэкенда (в т.ч. кастомный CLI-wrapper) и обвязку цепочек под прямые вызовы. Сигнал к пересмотру: LangChain-обёртка над `claude -p` начинает ломаться на каждом апдейте фреймворка либо native tool use становится доступен на обоих путях — тогда structured output стоит пересмотреть отдельным ADR.
